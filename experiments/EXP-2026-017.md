# EXP-2026-017 — Mini Inference Engine Latency vs Throughput

**Date:** 2026-09-03

---

## 1. Objective

Measure the latency/throughput trade-off of the mini inference engine under different continuous-batching concurrency levels.

The experiment compares:

* Batch/concurrency = 1
* Batch/concurrency = 8
* Batch/concurrency = 32

The objective is to empirically demonstrate how increasing concurrency affects:

* Time to First Token (TTFT)
* Inter-Token Latency (ITL)
* Tail latency (p95)
* Aggregate output-token throughput
* Peak GPU memory allocation

---

## 3. Benchmark Command

The latency/throughput experiment was executed with:

```bash
python bench/run_latency_curve.py \
    --max-total-active-tokens 32768
```

The benchmark automatically executed:

```text
batch1.yaml
batch8.yaml
batch32.yaml
```

For each workload:

1. The model was loaded.
2. Two warmup runs were executed.
3. Warmup results were discarded.
4. Ten measured repetitions were executed.
5. Per-request metrics were aggregated.
6. Peak GPU memory allocation was recorded.
7. Results were added to the final comparison.
8. The latency/throughput curve was generated.

## 4. Measurement Methodology

### TTFT

TTFT measures the time from request arrival to the first generated token:

```text
TTFT = first_token_time - arrival_time
```

### ITL

ITL measures the time between consecutive generated tokens:

```text
ITL_i = token_timestamp_i - token_timestamp_(i-1)
```

### Throughput

Aggregate output-token throughput is:

```text
throughput = total_output_tokens / benchmark_wall_time
```

The benchmark uses `time.perf_counter()` for elapsed-time measurements.

CUDA synchronization is performed around the measured execution so GPU work is included in the timing.

### Peak GPU Memory

Peak GPU memory was measured using PyTorch's CUDA memory allocator statistics:

```python
torch.cuda.max_memory_allocated()
```

The peak-memory counter was reset after warmup and before the measured repetitions.

The reported value therefore represents the maximum amount of GPU memory actively allocated by PyTorch during the measured benchmark.

## 8. Observations

### 8.1 Increasing concurrency increases throughput

Throughput increased from:

```text
Batch 1  → 100.40 tok/s
Batch 8  → 273.02 tok/s
Batch 32 → 337.92 tok/s
```

From batch 1 to batch 32:

```text
337.92 / 100.40 ≈ 3.37×
```

Therefore, increasing concurrency produced approximately a **3.37× increase in aggregate output throughput**.

However, the gain was not linear.

Batch 1 → 8 produced a large throughput improvement:

```text
100.40 → 273.02 tok/s
```

while batch 8 → 32 produced a much smaller improvement:

```text
273.02 → 337.92 tok/s
```

This indicates diminishing throughput returns at higher concurrency for this workload and hardware.

---

### 8.2 Increasing concurrency increases TTFT

TTFT p50 increased substantially:

```text
Batch 1  : 15.63 ms
Batch 8  : 71.18 ms
Batch 32 : 259.45 ms
```

The batch-32 configuration therefore provides substantially higher aggregate throughput at the cost of much higher first-token latency.

Compared with batch 1, batch 32 increases median TTFT by approximately:

```text
259.45 / 15.63 ≈ 16.6×
```

---

### 8.3 Tail latency grows significantly

TTFT p95 increased from:

```text
16.18 ms
```

at batch 1 to:

```text
125.67 ms
```

at batch 8 and:

```text
486.96 ms
```

at batch 32.

This is particularly important because the p95 increase is much more severe than the median increase.

At batch 32, the p95 TTFT is almost half a second:

```text
486.96 ms
```

even though the system achieves its highest aggregate throughput.

This demonstrates why reporting only average or median latency would hide an important part of the user experience.

---

### 8.4 ITL also increases with concurrency

ITL p50 increased from:

```text
9.73 ms
```

at batch 1 to:

```text
27.65 ms
```

at batch 8 and:

```text
87.83 ms
```

at batch 32.

Therefore, larger batches improve aggregate throughput but also increase the time between generated tokens for individual requests.

---

### 8.5 GPU memory increases with concurrency

Peak GPU memory allocation increased from:

```text
Batch 1  : 1019.01 MB
Batch 8  : 1176.70 MB
Batch 32 : 1716.70 MB
```

From batch 1 to batch 32, peak allocated GPU memory increased by approximately:

```text
1716.70 - 1019.01
≈ 697.69 MB
```

or approximately:

```text
1.68×
```

the batch-1 memory footprint.

This is consistent with the additional active sequences and KV-cache state required at higher concurrency.

The experiment therefore shows that increasing concurrency affects not only latency and throughput, but also GPU memory consumption.

---

### 8.6 The throughput/latency/memory trade-off is visible

The experiment demonstrates a three-way systems trade-off:

```text
Higher concurrency
        │
        ├──→ Higher aggregate throughput
        │
        ├──→ Higher TTFT / ITL
        │
        └──→ Higher GPU memory usage
```

For this workload:

```text
Batch 1
  ↓
Low latency
Low memory
Low throughput

Batch 8
  ↓
Moderate latency
Moderate memory
Much higher throughput

Batch 32
  ↓
High latency
High memory
Highest throughput
```

The exact operating point depends on the application's latency and memory requirements.

For interactive generation, batch 32 may impose too much TTFT despite providing the highest throughput.

For throughput-oriented workloads, the additional latency and memory consumption may be acceptable.

## 10. Experimental Limitations

This experiment evaluates the mini inference engine on a single hardware configuration and model.

The results should therefore be interpreted as workload- and hardware-specific measurements rather than universal performance claims.

In particular:

* Only one model was evaluated.
* Only one dtype was evaluated.
* Only one prompt/output distribution was evaluated.
* GPU memory was measured using PyTorch's `max_memory_allocated()` rather than total device VRAM usage.
* The benchmark uses synthetic workload requests.
* The experiment does not compare against vLLM yet.
* The benchmark does not yet evaluate different sequence lengths or memory-pressure regimes.

The purpose of this experiment is to establish a controlled baseline for the mini engine before comparison with a production inference engine.

---

## 11. Conclusion

The experiment successfully demonstrates the fundamental latency/throughput trade-off of continuous batching.

Increasing concurrency from 1 to 32 increased aggregate throughput from:

```text
100.40 tok/s → 337.92 tok/s
```

representing approximately a:

```text
3.37×
```

increase in throughput.

At the same time:

```text
TTFT p50 : 15.63 ms  → 259.45 ms
TTFT p95 : 16.18 ms  → 486.96 ms
ITL p50  : 9.73 ms   → 87.83 ms
GPU mem  : 1019 MB   → 1717 MB
```

The results show that higher batching does not simply make inference "faster."

Instead, it trades:

**individual request latency + GPU memory**

for:

**higher aggregate system throughput.**

The experiment therefore provides a quantitative baseline for evaluating the mini inference engine and establishes the latency/throughput/memory behavior that can later be compared against vLLM.
