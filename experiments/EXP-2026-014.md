

# EXP-2026-014 - Static vs Continuous Batching

## 1. Experiment Overview

**Experiment:** Static vs Continuous Throughput Experiment

**Experiment ID:** EXP-2026-014

**Model:** `Qwen/Qwen2.5-0.5B-Instruct`

**Batch size cap:** 2

**Device:** CUDA when available

**Dtype:** BF16

**Sampling:** Greedy (`temperature=0.0`)

### Objective

Measure the throughput and latency behavior of static batching versus continuous batching under the **same request workload**, with deliberately variable output lengths.

The purpose of this experiment is to determine whether continuous batching improves system-level efficiency when requests finish at different times.

The primary hypothesis is:

> Continuous batching should improve aggregate throughput and reduce tail latency because finished requests can be replaced by waiting requests instead of leaving inactive batch slots unused.

---

## 2. Workload

Both schedulers receive the exact same six requests in the exact same order.

All requests have a prompt length of 32 tokens, while their requested output lengths vary.

| Request | Prompt Length | Max New Tokens |
| ------- | ------------: | -------------: |
| r1      |            32 |              8 |
| r2      |            32 |             32 |
| r3      |            32 |             64 |
| r4      |            32 |             16 |
| r5      |            32 |             48 |
| r6      |            32 |              8 |

Total requested output tokens:

$$
8 + 32 + 64 + 16 + 48 + 8 = 176
$$

The workload intentionally contains substantial output-length variance:

$$
L_{\min}=8,\qquad L_{\max}=64
$$

with a maximum-to-minimum ratio of:

$$
\frac{64}{8}=8
$$

This length variance is important because continuous batching is most useful when requests do not finish at the same time.

---

## 3. Batch Configuration

Both experiments use:

```text
max_batch_size = 2
```

The continuous scheduler additionally uses:

```text
max_total_active_tokens = 10000
max_waiting = 6
```

The maximum batch size is therefore identical between the two approaches.

The workload itself is also identical.

The key difference is **how requests are managed after a request finishes**.

---

## 4. Static Batching

Static batching divides the workload into fixed batches of at most two requests:

```text
Batch 1: r1, r2
Batch 2: r3, r4
Batch 3: r5, r6
```

Once a static batch has been formed, its membership does not change.

The implementation uses the existing cached execution path:

```text
forward_prefill_cached()
        ↓
forward_decode_cached()
```

Each request owns its KV cache.

When a request reaches EOS or its requested maximum number of generated tokens, its slot is no longer useful for generation, but the remaining request in that static batch continues.

For example:

```text
r1: 8 tokens
r2: 32 tokens
```

After `r1` finishes:

```text
Step 1–8:
    r1 + r2

Step 9–32:
    idle slot + r2
```

The unused capacity cannot be assigned to another waiting request because static batching keeps the batch membership fixed.

---

## 5. Continuous Batching

Continuous batching maintains a waiting queue and an active set.

The scheduler repeatedly:

1. Evicts finished requests.
2. Admits waiting requests when capacity is available.
3. Decodes one token for every active request.
4. Repeats until all requests finish.

Conceptually:

```text
Waiting Queue
      │
      ▼
   Scheduler
      │
      ▼
 Active Requests
      │
      ▼
 Decode one token
      │
      ▼
 Finished?
   /       \
 yes        no
  │          │
  ▼          │
Evict        │
  │          │
  ▼          │
Admit waiting◄┘
```

The continuous implementation uses the ragged decode path:

```text
forward_decode_ragged()
```

Each active request maintains its own KV cache and decode position.

When a request finishes, another waiting request can be admitted without waiting for the other active requests in the previous batch to finish.

---

## 6. Metrics

### Throughput

Aggregate generated-token throughput is:

$$
\text{Throughput}
=
\frac{N_{\text{output tokens}}}{T_{\text{experiment}}}
$$

where \(N_{\text{output tokens}}\) is the total number of generated tokens and \(T_{\text{experiment}}\) is the measured wall-clock execution time.

### TTFT

Time to first token is measured as:

$$
\mathrm{TTFT}
=
t_{\text{first token}}
-
t_{\text{prefill start}}
$$

Both p50 and p95 are reported.

### ITL

For consecutive generated tokens:

$$
\mathrm{ITL}_i
=
t_i-t_{i-1}
$$

All inter-token intervals are collected across requests, and p50 and p95 are reported.

### Total latency

For each request:

$$
T_{\text{total}}
=
t_{\text{finish}}
-
t_{\text{arrival}}
$$

Both p50 and p95 are reported.

## 8. Aggregate Results

The average across the three runs is:

| Metric                 |    Static |  Continuous |
| ---------------------- | --------: | ----------: |
| Throughput (tok/s)     |     45.28 |   **85.93** |
| TTFT p50 (ms)          |     20.25 |   **20.06** |
| TTFT p95 (ms)          |    458.36 |   **21.16** |
| ITL p50 (ms)           | **18.68** |       21.23 |
| ITL p95 (ms)           |     38.21 |   **21.76** |
| Total latency p50 (ms) |   2415.73 | **1345.06** |
| Total latency p95 (ms) |   3707.30 | **1980.74** |

The continuous batching throughput improvement is approximately:

$$
\frac{85.93-45.28}{45.28}\times100
\approx89.8\%
$$

or approximately:

$$
\boxed{1.90\times}
$$

the throughput of static batching.

---

## 9. Analysis

### 9.1 Throughput

The strongest result is aggregate throughput.

Static batching averaged approximately:

```text
45.28 tokens/s
```

while continuous batching averaged:

```text
85.93 tokens/s
```

This represents an approximately **90% throughput improvement**.

The total number of generated tokens was identical:

```text
Static:      176 tokens
Continuous:  176 tokens
```

Therefore, the throughput difference is not caused by generating more tokens in the continuous experiment.

The improvement comes from completing the same workload in less wall-clock time.

---

### 9.2 Static batching wastes capacity

The workload contains requests with very different output lengths.

Consider:

```text
r1 = 8 tokens
r2 = 32 tokens
```

With static batching:

```text
Token step:

1  2  3  4  5  6  7  8  9 ... 32
│  │  │  │  │  │  │  │  │     │
r1 █  █  █  █  █  █  █  █
r2 █  █  █  █  █  █  █  █  █ ... █
```

After `r1` finishes, its batch slot cannot be given to another waiting request.

The same effect occurs more strongly for:

```text
r3 = 64 tokens
r4 = 16 tokens
```

After `r4` finishes, `r3` continues for another 48 generation steps while the second static slot is unused.

Continuous batching avoids this waste by replacing finished requests:

```text
r3 ─────────────────────────────────────
r4 ────────────────┐
                   │ finishes
                   ▼
r5 ────────────────────────────────
```

Thus, available batch capacity is reused by waiting requests.

---

### 9.3 TTFT

Median TTFT is almost identical:

```text
Static:      20.25 ms
Continuous:  20.06 ms
```

This indicates that the basic prefill cost is similar.

The difference becomes much larger at the tail:

```text
Static p95:       458.36 ms
Continuous p95:    21.16 ms
```

The continuous scheduler avoids the long waiting behavior associated with fixed batch groups.

Therefore, continuous batching provides a particularly large improvement in **TTFT tail latency** for this workload.

---

### 9.4 ITL

ITL p50 is slightly worse with continuous batching:

```text
Static:       18.68 ms
Continuous:   21.23 ms
```

This is not considered a failure of continuous batching.

Continuous batching is primarily a scheduling strategy for improving aggregate system utilization and reducing queueing/tail effects. It does not guarantee lower per-token latency for every individual decode step.

The small increase in median ITL can come from the additional scheduling and ragged-batch management performed on every step.

However, the ITL tail improves substantially:

```text
Static p95:       38.21 ms
Continuous p95:   21.76 ms
```

Thus, continuous batching trades a small increase in median ITL for a significant improvement in ITL tail behavior and overall throughput.

---

### 9.5 Total latency

Total latency improves substantially under continuous batching.

Median:

```text
Static:       2415.73 ms
Continuous:   1345.06 ms
```

95th percentile:

```text
Static:       3707.30 ms
Continuous:   1980.74 ms
```

The p50 reduction is approximately:

$$
\frac{2415.73-1345.06}{2415.73}\times100
\approx44.3\%
$$

The p95 reduction is approximately:

$$
\frac{3707.30-1980.74}{3707.30}\times100
\approx46.6\%
$$

This demonstrates that the scheduler improvement affects not only aggregate throughput but also end-to-end request completion time.

---

## 10. Why Continuous Batching Helps

The key difference can be summarized as:

### Static batching

```text
Fixed batch
    │
    ├── Request A ──────── finish
    │
    └── Request B ───────────────────── finish

After A finishes:
    └── unused capacity
```

### Continuous batching

```text
Active batch
    │
    ├── Request A ──────── finish
    │                         │
    │                         ▼
    │                    admit Request C
    │                         │
    └── Request B ───────────────────── finish
```

Continuous batching therefore keeps the available batch capacity useful for a larger fraction of the experiment.

The benefit becomes larger as:

* output lengths become more variable,
* concurrency increases,
* requests finish at different times,
* and the GPU has enough work to benefit from batching.

---

## 11. Conclusion

Under the defined workload, continuous batching substantially outperformed static batching.

The average throughput increased from:

$$
45.28\rightarrow85.93\ \text{tokens/s}
$$

which corresponds to approximately:

$$
\boxed{1.90\times}
$$

higher throughput.

At the same time, continuous batching reduced:

* TTFT p95 from **458.36 ms → 21.16 ms**
* ITL p95 from **38.21 ms → 21.76 ms**
* total latency p50 from **2415.73 ms → 1345.06 ms**
* total latency p95 from **3707.30 ms → 1980.74 ms**

Median ITL increased modestly from **18.68 ms to 21.23 ms**, demonstrating that improved system throughput does not necessarily imply lower per-token latency.

The experiment therefore supports the hypothesis that **continuous batching is particularly beneficial for workloads with variable output lengths**, because it prevents finished requests from leaving unused capacity inside otherwise active static batches.
