# EXP-2026-015 — Contiguous KV Memory Baseline and Fragmentation

## Experiment

**Experiment ID:** EXP-2026-015
**Objective:** Contiguous KV memory baseline and fragmentation measurement
**Status:** Complete
**Date:** 2026-08-31

---

## Objective

Measure the memory waste caused by reserving a fixed `max_seq_len` KV-cache capacity for every active request.

The purpose of this experiment is to establish the **contiguous KV-cache baseline** before implementing paged KV memory.

The experiment measures:

* reserved KV capacity
* actually used KV capacity
* wasted capacity
* waste ratio
* sensitivity to `max_seq_len`

The central question is:

> How much KV-cache capacity is reserved but unused when active requests have different current sequence lengths?

---

## Implementation

The baseline allocator is implemented in:

```text
engine/contiguous_cache.py
```

The allocator represents one contiguous KV-cache reservation per request.

For a configured:

```text
max_seq_len = L_max
```

each request receives:

```text
reserved_tokens = L_max
```

regardless of its current sequence length.

Each allocation tracks:

```text
request_id
reserved_tokens
used_tokens
wasted_tokens
```

The cache also maintains aggregate values across all active requests:

```text
reserved_tokens
used_tokens
wasted_tokens
waste_ratio
```

---

## Allocation Model

For request \(i\), let:

$$
L_i
$$

be the number of tokens currently used by the request.

The contiguous allocator reserves:

$$
R_i = L_{\max}
$$

tokens.

Therefore the unused capacity for request \(i\) is:

$$
W_i = R_i - L_i
$$

or:

$$
W_i = L_{\max} - L_i
$$

For \(N\) active requests:

$$
R = \sum_{i=1}^{N} R_i
$$

$$
U = \sum_{i=1}^{N} L_i
$$

$$
W = R-U
$$

where:

* \(R\) = total reserved capacity
* \(U\) = total used capacity
* \(W\) = total wasted capacity

---

## Waste Ratio

The fragmentation/waste ratio is defined as:

$$
\text{Waste Ratio}
=
\frac{W}{R}
$$

Substituting:

$$
\text{Waste Ratio}
=
\frac{R-U}{R}
$$

or equivalently:

$$
\text{Waste Ratio}
=
1-\frac{U}{R}
$$

The metric represents the fraction of reserved KV capacity that is not currently being used.

---

## Actual KV Memory

The token-level measurements can be converted into bytes using the KV-cache size per token.

For a transformer with:

* \(L\) transformer layers
* \(H_{kv}\) key/value heads
* \(d_h\) head dimension
* \(b\) bytes per element

one token requires:

$$
M_{\text{token}}
=
2LH_{kv}d_hb
$$

bytes.

The factor \(2\) accounts for storing both:

$$
K
$$

and:

$$
V
$$

Therefore:

$$
M_{\text{reserved}}
=
R\cdot M_{\text{token}}
$$

$$
M_{\text{used}}
=
U\cdot M_{\text{token}}
$$

and:

$$
M_{\text{wasted}}
=
W\cdot M_{\text{token}}
$$

Because the same bytes-per-token factor applies to reserved and used capacity, the waste ratio is identical whether measured in tokens or bytes:

$$
\frac{M_{\text{wasted}}}
     {M_{\text{reserved}}}
=
\frac{W}{R}
$$

# Workload

The experiment uses four simultaneously active requests with different current sequence lengths:

```text
r1:  64 tokens
r2: 128 tokens
r3: 256 tokens
r4: 384 tokens
```

Therefore:

$$
U = 64+128+256+384
$$

$$
U = 832
$$

The same active workload is evaluated with three different contiguous reservation sizes:

```text
512
1024
2048
```

This isolates the effect of increasing `max_seq_len`.

```text
Active requests:       4

    512

    2048
```

The workload is intentionally kept constant across the three experiments.

Only the reservation size changes.

# Analysis

The used capacity remains constant:

$$
U=832
$$

because the active workload does not change.

However, the reserved capacity scales linearly with `max_seq_len`:

$$
R=N L_{\max}
$$

For four requests:

### `max_seq_len = 512`

$$
R=4(512)=2048
$$

$$
W=2048-832=1216
$$

$$
\text{Waste Ratio}
=
\frac{1216}{2048}
\approx 59.38\%
$$

### `max_seq_len = 1024`

$$
R=4(1024)=4096
$$

$$
W=4096-832=3264
$$

$$
\text{Waste Ratio}
\approx79.69\%
$$

### `max_seq_len = 2048`

$$
R=4(2048)=8192
$$

$$
W=8192-832=7360
$$

$$
\text{Waste Ratio}
\approx89.84\%
$$

The result demonstrates that increasing the reservation size without increasing actual sequence utilization produces substantially greater internal fragmentation.

---

# Interpretation

The important observation is not simply that memory is wasted.

It is that **the unused capacity is trapped inside allocations already owned by active requests**.

For example, with:

```text
max_seq_len = 2048
```

the system reserves:

```text
8192 tokens
```

for four requests, while only:

```text
832 tokens
```

are currently used.

Therefore:

```text
7360 tokens
```

of reserved capacity are unavailable for other requests despite not containing useful KV data.

This limits the number of requests that can be admitted concurrently when GPU memory is the limiting resource.

---

# Why This Motivates Paged KV Memory

The contiguous baseline creates a structural problem:

```text
Request
   |
   v
One large contiguous reservation
   |
   +-----------------------------+
   | used |       unused         |
   +-----------------------------+
```

The allocation size is determined by the maximum possible sequence length rather than the current sequence length.

Paged KV memory changes this model by dividing KV memory into fixed-size blocks:

```text
KV memory pool

+--------+--------+--------+--------+--------+
| block0 | block1 | block2 | block3 | block4 |
+--------+--------+--------+--------+--------+
```

A request only needs enough blocks to contain its current KV state.

Unused space is then limited primarily to the partially filled final block rather than an entire large per-request reservation.

This experiment therefore establishes the baseline against which the later block-based allocator can be compared.

---

# Limitations

This experiment measures **capacity fragmentation**, not end-to-end GPU performance.

It does not yet implement:

* physical KV blocks
* a free-list allocator
* logical-to-physical block tables
* paged attention
* block-level KV allocation
* GPU memory allocation
* kernel-level memory-access effects

The workload is also a synthetic snapshot of active sequence lengths rather than a trace of real request arrivals.

These mechanisms are introduced in subsequent milestones.

---

# Conclusion

This expirement establishes the contiguous KV-cache baseline.

For the fixed active workload:

$$
[64,128,256,384]
$$

only:

$$
832
$$

tokens are actually used.

As the per-request reservation increases from `512` to `2048` tokens, the measured waste ratio increases from:

$$
59.38\%
$$

to:

$$
89.84\%
$$

This demonstrates the fragmentation problem that motivates paged KV memory.

The next milestone replaces the single contiguous reservation model with a **fixed-size block pool and free-list allocator**.
