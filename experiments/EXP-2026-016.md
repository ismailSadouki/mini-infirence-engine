# EXP-2026-016 — Paged vs Contiguous KV Memory Utilization

## Objective

Measure the memory-utilization advantage of paged KV caching over contiguous per-sequence KV buffers under a fixed KV-memory budget.

The experiment focuses on **memory utilization and concurrent sequence capacity**, not execution speed.

The central question is:

> How many more concurrent sequences can fit into the same KV-memory budget when KV cache storage is allocated in blocks instead of reserving a full maximum-length buffer for every sequence?

---

## Experimental Setup

### Model KV configuration

The experiment uses the KV-cache configuration of the target Qwen model.

| Parameter                        |             Value |
| -------------------------------- | ----------------: |
| KV bytes/token                   |      12,288 bytes |
| KV dtype                         |              BF16 |
| Maximum sequence length          |      2,048 tokens |
| Memory budget                    |          1.00 GiB |
| Number of sequences per workload |             1,000 |
| Block sizes                      | 16, 32, 64 tokens |

The KV memory required for one token is:

```text
2 × num_layers × num_kv_heads × head_dim × bytes_per_element
= 12,288 bytes/token
```

The factor of 2 accounts for storing both K and V.

---

## Workload Distributions

Three deterministic sequence-length distributions were used.

### Many short

Sequences are sampled between 8 and 64 tokens.

This represents workloads dominated by short requests.

### Mixed

Sequences are sampled across several length ranges:

```text
8–64
65–256
257–768
769–1536
1537–2048
```

This represents a heterogeneous serving workload.

### Many long

Sequences are sampled between 512 and 2048 tokens.

This represents workloads dominated by long-running sequences.

A fixed random seed (`2026`) is used so that the workload is reproducible.

---

## Memory Model

### Contiguous KV cache

Each sequence reserves space for the maximum sequence length:

```text
reserved KV = num_sequences × max_seq_len × bytes_per_token
```

Therefore, a sequence containing only 32 tokens still reserves space for 2,048 tokens.

The actual KV usage remains:

```text
used KV = total_tokens × bytes_per_token
```

The difference between reserved and used memory represents unused capacity caused by per-sequence over-allocation.

### Paged KV cache

Paged KV divides the cache into fixed-size blocks.

For a sequence of length `L` and block size `B`:

```text
allocated blocks = ceil(L / B)

reserved tokens = ceil(L / B) × B
```

Only the final block can contain unused positions.

Therefore, paged KV reduces **internal fragmentation**, but does not reduce the actual KV bytes required to store real tokens.

# Results

## Memory utilization

### Many short

The workload contains 1,000 sequences and 36,899 total tokens.

| Configuration |      Reserved | Actual used | Savings vs contiguous |
| ------------- | ------------: | ----------: | --------------------: |
| Contiguous    | 24,000.00 MiB |  432.41 MiB |                     — |
| Paged, B=16   |    513.75 MiB |  432.41 MiB |                97.86% |
| Paged, B=32   |    595.88 MiB |  432.41 MiB |                97.52% |
| Paged, B=64   |    750.00 MiB |  432.41 MiB |                96.88% |

Paged KV dramatically reduces reserved memory for short sequences.

Block size 16 provides the lowest reservation because it minimizes unused space in the final block.

# Concurrent Sequence Capacity

The fixed KV-memory budget is 1 GiB.

With contiguous allocation, each sequence reserves:

```text
2048 × 12,288 bytes
```

which allows:

```text
42 concurrent sequences
```

under the 1 GiB budget.

The estimated paged capacities are:

| Workload   | Contiguous | Paged B=16 | Paged B=32 | Paged B=64 |
| ---------- | ---------: | ---------: | ---------: | ---------: |
| Many short |         42 |  **1,993** |      1,718 |      1,365 |
| Mixed      |         42 |    **128** |        126 |        124 |
| Many long  |         42 |     **68** |         68 |         67 |

Relative to the contiguous baseline:

| Workload   |       B=16 |   B=32 |   B=64 |
| ---------- | ---------: | -----: | -----: |
| Many short | **47.45×** | 40.90× | 32.50× |
| Mixed      |  **3.05×** |  3.00× |  2.95× |
| Many long  |  **1.62×** |  1.62× |  1.60× |

The largest capacity advantage occurs for workloads containing many short sequences.

# Block-Size Trade-off

The experiment also measures unused space caused by the partially filled final block.

### Many short

| Block size |  Waste |
| ---------- | -----: |
| 16         | 15.83% |
| 32         | 27.43% |
| 64         | 42.35% |

### Mixed

| Block size | Waste |
| ---------- | ----: |
| 16         | 1.10% |
| 32         | 2.25% |
| 64         | 4.40% |

### Many long

| Block size | Waste |
| ---------- | ----: |
| 16         | 0.60% |
| 32         | 1.20% |
| 64         | 2.44% |

The trend is consistent across all workloads:

```text
larger block size
        ↓
more unused space in final blocks
        ↓
higher internal fragmentation
```

The effect is strongest for short sequences.

# Interpretation

The experiment demonstrates the primary memory advantage of paged KV caching.

Contiguous allocation reserves a maximum-sized KV buffer for every active sequence. This creates substantial unused capacity when actual sequence lengths are much shorter than the maximum.

Paged KV instead allocates memory in fixed-size blocks. Consequently, reserved memory tracks actual sequence lengths much more closely.

The results show that:

1. **Paged KV dramatically reduces memory over-allocation for short sequences.**
2. **Smaller blocks reduce internal fragmentation.**
3. **The capacity advantage is workload-dependent.**
4. **For long sequences, block-size fragmentation becomes relatively small.**
5. **Paged KV can substantially increase the number of concurrent sequences that fit under a fixed KV-memory budget.**

For the many-short workload, block size 16 increases estimated concurrent capacity from 42 to 1,993 sequences, a **47.45× increase** over the contiguous baseline.

This should be interpreted strictly as a **memory-capacity result**, not a throughput or latency improvement.

---

# Limitations

This experiment models KV memory allocation mathematically rather than measuring GPU allocator behavior directly.

In particular:

* It does not measure CUDA kernel execution time.
* It does not measure TTFT.
* It does not measure inter-token latency.
* It does not measure throughput.
* It does not account for Python-level gathering overhead.
* The capacity estimate uses the average paged memory requirement of each workload distribution.

Therefore, the results demonstrate the **memory-utilization mechanism** behind paged KV caching rather than claiming that paged attention is faster.

---

# Conclusion

Paged KV caching substantially reduces internal fragmentation compared with contiguous per-sequence KV buffers.

The benefit is especially large when serving many short or heterogeneous sequences, where reserving a full maximum-length buffer would leave most of the allocated memory unused.

Block size controls the trade-off: smaller blocks reduce fragmentation, while larger blocks increase unused capacity in partially filled final blocks.

The experiment therefore validates the expected memory-level behavior of paged KV caching and provides the baseline for the next stage of the inference engine:

**measuring actual serving performance through TTFT, inter-token latency, and throughput benchmarks.**
